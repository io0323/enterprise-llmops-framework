## 2. 週次(5-10分)

```bash
llmops report weekly --out output/weekly_$(date +%Y%m%d).md
```

このレポートで**必ず見る4つ**:

| 見るもの | 異常のサイン | 対応 |
|---|---|---|
| `degraded` 件数 | **0 より大きい**(本来ありえない) | 本番の論理モデルは `fallback_to` を持たない(NOTES.md N-026)。0 でないなら **`models.yaml` に `fallback_to` が復活している**。`llmops model list` で `→ fallback=` が出ていないか確認し、外す |
| 失敗spanのコスト | 全体の10%超 | リトライで捨てているコストが多い。Prompt側の出力形式指示が弱い可能性 |
| stale資産 | 90日未使用が増えている | 使われていないPromptの棚卸し。`llmops prompt deprecate` |
| 使われ方の異常 | 1件以上出ている | **予算では止まらないぶんの見張り**(NOTES.md N-046)。予算対象外(サブスク換算)のコスト、または trace 生成数が、直近の中央値に対して跳ねている。下記の手順で原因を切り分ける |

### 「使われ方の異常」が出たとき

予算(`budgets`)が見るのは実課金ぶんだけで、`claude -p` のコストは対象外(N-045)。
対象外のぶんには**金額の上限を置いていない**ので、暴走はこの項目でしか気付けない。

検知は「直近7日の中央値の3倍以上、かつ日額5 USD以上(または日次20 trace以上)」。
閾値は `config.yaml` の `anomaly:` にある。**これは上限ではないので、自動では止まらない。
止めるかどうかは人が決める。**

```bash
# 1. どの system の、どの日が跳ねているかを見る(レポートに出ている)
llmops report cost --since 14d --by system

# 2. その日の trace を数と operation で見る。同じ operation が並んでいたら暴走を疑う
llmops trace list --since 2d

# 3. 二重起動していないか(DDE/CGMP のスケジューラ、Harness の APScheduler)
#    リトライループになっていないか(同一 external_id の trace が何本もある)
```

よくある原因は、スケジューラの二重起動・失敗したジョブの無限リトライ・
バッチ対象の絞り込み漏れ。いずれもコードの問題なので、上限で抑えるのではなく直す。
心当たりがあって正常なら(記事をまとめて作った等)、そのまま放置してよい。

`degraded` は「LLM が不調だった」のサインではなく、**設定が変わったことのサイン**である。
`chat-fallback`(mock)へ落ちると、プロンプトをそのまま返した出力が
「それらしい結果」として通りうる(実際に CGMP の品質評価で偽のスコアが出た)。
本番モデルの Fallback は意図的に外してあるので、`degraded` が立つこと自体が異常。

### 閉ループの週次作業(これを飛ばすと評価が陳腐化する)

```bash
# 1. 先週の失敗を確認する
llmops trace list --status failed --since 7d
llmops trace show <trace_id> --full          # 入出力全文を見て、再発させたくないものを選ぶ

# 2. 再発させたくない失敗を回帰ケースに変換する
llmops eval add-case cgmp-section --from-span <span_id>

# 3. 変換したケースの変数を補う
#    span に残っているのは**レンダリング後のテキスト**なので、変数そのものは
#    復元できない。add-case は復元できなかった変数名を出すので、それを手で埋める
#    (推測で埋めない設計にしてある。偽のケースは偽の合格を生むため)

# 4. 追加したケースを含めて評価し直す
llmops eval run cgmp-section
llmops eval report <run_id>
```

**この操作が回らないとPhase 2全体が飾りになる。** 週1件でもいいので必ず追加する。
`llmops eval report` の「ケースの出自内訳」で production-failure 由来が増えているか確認する。
0件のままなら、レポートが陳腐化の警告を出す。

### 評価まわりで「止まった」ときの読み方

| verdict | 意味 | すること |
|---|---|---|
| `pass` | 合格 | publish できる |
| `fail` | 決定的評価の不合格 / degraded 混入 / スコア欠損 | レポートの「判定理由」を読む |
| `regressed` | ベースライン比で劣化 | 前の版と diff を取る(`llmops prompt diff`) |
| `wiring_check` | **品質を判定していない**(mock 経由) | 実モデルで流し直す。publish の根拠にはならない |

`fail` で「degraded の span が混ざっている」と出たら、**中身を見る前に設定を疑う**。
本番の論理モデルは `fallback_to` を持たないので(N-026)、degraded が立つのは
`models.yaml` に Fallback が復活しているときだけである。`llmops model list` で確認して外す。
縮退実行の結果で品質を判定しない設計にしてあるため、verdict は無条件で fail になる。

「採点失敗 N 件」が出たら Judge 自体の健全性を疑う。Judge の応答が
期待スキーマに合わないケースで、スコアは**欠損として平均から除外**されている
(0点にはしていない)。`llmops report quality` にパース失敗率が出る。

## 3. Prompt を変更するとき

```bash
# 1. ファイルを編集
vim prompts/cgmp/section.md

# 2. 取り込み(新versionが採番される)
llmops sync

# 3. レンダリング結果を目視確認(実行はしない・コストゼロ)
llmops prompt render cgmp.section --vars tests/fixtures/section_vars.json
llmops prompt diff cgmp.section 3 4

# 4. 評価
llmops eval run cgmp-section --baseline

# 5. 結果を見て判断
llmops eval report <run_id>

# 6. 問題なければ公開(評価ゲートを通らないと失敗する)
llmops prompt submit cgmp.section
llmops prompt approve cgmp.section
llmops prompt publish cgmp.section
```

アプリ側(CGMP)の再デプロイは不要。次回実行から新版が使われる。

### 自信がないとき

```bash
llmops prompt canary cgmp.section --version 4 --percent 10
# 数日運用してから
llmops report quality --compare-canary cgmp.section
llmops prompt promote cgmp.section     # または rollback
```

### 失敗したとき

```bash
llmops prompt rollback cgmp.section     # 直前のpublished版へ。5分以内
```

## 5. 調査手順(品質が悪い出力を見つけたとき)

```bash
# 1. 該当記事のIDからtraceを引く
llmops trace show <cgmp_request_id>

# 出るもの: 各LLM呼び出しの prompt_id@version / モデル / render_hash /
#           所要時間 / コスト / 成否 / degraded

# 2. 入出力の全文を見る
llmops trace show <cgmp_request_id> --full

# 3. 同じPrompt版の他のspanと比較する
sqlite3 data/llmops.sqlite3 \
  "SELECT id,success,degraded,output_tokens FROM spans
   WHERE prompt_id='cgmp.section' AND prompt_version=4 ORDER BY created_at DESC LIMIT 20;"

# 4. 原因がPromptなら、その入力を回帰ケースにしてから直す
llmops eval add-case cgmp-section --from-span <span_id>
```

**順序が重要**: ケースを追加してから直す。直してから追加すると「直った状態」がケースになり、
回帰を検出できない。

## 6. トラブル対応

| 症状 | 確認 | 対応 |
|---|---|---|
| 全呼び出しが失敗する | `claude -p "ping" --output-format json` | Claude Code側の問題。**ELFは代替モデルへ落とさない**(N-026)。再試行を使い切って `AllProvidersFailed` になり、アプリ側は `LLMError` として扱う。span は失敗として全件残るので `llmops trace list --status failed --since 1d` で範囲を確認する。復旧まで待つのが正しい対処で、`fallback_to` を足して mock で凌ぐことはしない(偽の結果が本番データに混ざる) |
| `QuotaExceeded` が出る | `llmops budget show` | 予算到達。意図的なら `llmops budget set` で引き上げる。意図せずなら原因のtraceを特定する |
| `LLMBudgetExceeded` が出る | `llmops trace show <id>` | 1trace内の呼び出しが上限(既定10回)に到達。無限ループの疑い。**上限を上げる前に原因を見る** |
| `PromptNotPublished` | `llmops prompt show <id>` | 状態が published でない。approve → publish を通す |
| spanが記録されない | `logs/llmops.log` の WARN | Tracerがbest-effortで握り潰している。DBロック・ディスク容量を確認 |
| 応答のcost/tokenがNULL | `spans.raw_response_json` を見る | `claude` CLI の応答スキーマが変わった可能性。`raw` から再集計できる |
| DBが肥大化 | `du -h data/llmops.sqlite3` | `llmops retention apply --dry-run`(Phase 3) |

## 7. やってはいけないこと

| 禁止 | 理由 |
|---|---|
| `allow_unpublished: true` を本番のまま放置 | 評価ゲートが無効になる。開発時のみ |
| `allow_raw_completion: true` を移行後も残す | Registry管理外の呼び出しが恒久化し、Prompt外部化の意味が消える |
| `--force` publish の常用 | 評価ゲートの形骸化。使うたびに監査ログに残ることを意識する |
| `guard.calls_per_trace_limit` を安易に上げる | 上限に当たるのは大抵バグ。上限は症状であって原因ではない |
| Promptの文言改善と構造変更を同時にやる | どちらが原因でスコアが動いたか分からなくなる |
| 評価スイートに production-failure ケースを追加しない | 数ヶ月でスイートが陳腐化し、評価が通るのに本番が壊れる状態になる |
| 既存5システムのコードを移行手順外で触る | 長期テスト中。回帰が最大のリスク |
