## 1. 日次(自動・確認は不要)

DDE/CGMP/Harness の実行に伴い、ELFは自動で記録する。人が何かする必要はない。

自動で起きること: trace/span記録、`cost_daily` 更新、予算警告のログ出力、Quota超過時の遮断。

## 2. 週次(5-10分)

```bash
llmops report weekly --out output/weekly_$(date +%Y%m%d).md
```

このレポートで**必ず見る3つ**:

| 見るもの | 異常のサイン | 対応 |
|---|---|---|
| `degraded` 件数 | 0より大きい | Fallbackが発生している。`claude -p` の不調か設定ミス。`llmops model health` で確認 |
| 失敗spanのコスト | 全体の10%超 | リトライで捨てているコストが多い。Prompt側の出力形式指示が弱い可能性 |
| stale資産 | 90日未使用が増えている | 使われていないPromptの棚卸し。`llmops prompt deprecate` |

### 閉ループの週次作業(これを飛ばすと評価が陳腐化する)

```bash
# 先週の失敗を確認
llmops trace list --status failed --since 7d

# 再発させたくない失敗を回帰ケースに変換
llmops eval add-case cgmp-section --from-span <span_id>
```

**この操作が回らないとPhase 2全体が飾りになる。** 週1件でもいいので必ず追加する。
`llmops eval report` の「ケース出自内訳」で production-failure 由来が増えているか確認する。

## 3. Prompt を変更するとき

```bash
# 1. ファイルを編集
vim prompts/cgmp/section.md

# 2. 取り込み(新versionが採番される)
llmops sync

# 3. レンダリング結果を目視確認(実行はしない・コストゼロ)
llmops prompt render cgmp.section --vars tests/fixtures/section_vars.json
llmops prompt diff cgmp.section 3 4

# 4. 評価
llmops eval run cgmp-section --baseline

# 5. 結果を見て判断
llmops eval report <run_id>

# 6. 問題なければ公開(評価ゲートを通らないと失敗する)
llmops prompt submit cgmp.section
llmops prompt approve cgmp.section
llmops prompt publish cgmp.section
```

アプリ側(CGMP)の再デプロイは不要。次回実行から新版が使われる。

### 自信がないとき

```bash
llmops prompt canary cgmp.section --version 4 --percent 10
# 数日運用してから
llmops report quality --compare-canary cgmp.section
llmops prompt promote cgmp.section     # または rollback
```

### 失敗したとき

```bash
llmops prompt rollback cgmp.section     # 直前のpublished版へ。5分以内
```

## 4. 月次(15分)

```bash
llmops report cost --since 30d --by system
llmops report cost --since 30d --by prompt
llmops budget show
llmops catalog list --stale-days 90
llmops policy check
```

見るべき点:

- **¥/解決タスク**(trace単価)の推移。span単価ではなくこちらを見る。
  リトライが増えると span単価が変わらなくてもtrace単価は上がる
- 予算の予測消化率。月末に上限へ当たりそうなら、`chat-fast` へ寄せるかPromptを短くする
- Policy違反。`--force` publish が使われていないか(`llmops audit tail --event prompt.publish`)

## 5. 調査手順(品質が悪い出力を見つけたとき)

```bash
# 1. 該当記事のIDからtraceを引く
llmops trace show <cgmp_request_id>

# 出るもの: 各LLM呼び出しの prompt_id@version / モデル / render_hash /
#           所要時間 / コスト / 成否 / degraded

# 2. 入出力の全文を見る
llmops trace show <cgmp_request_id> --full

# 3. 同じPrompt版の他のspanと比較する
sqlite3 data/llmops.sqlite3 \
  "SELECT id,success,degraded,output_tokens FROM spans
   WHERE prompt_id='cgmp.section' AND prompt_version=4 ORDER BY created_at DESC LIMIT 20;"

# 4. 原因がPromptなら、その入力を回帰ケースにしてから直す
llmops eval add-case cgmp-section --from-span <span_id>
```

**順序が重要**: ケースを追加してから直す。直してから追加すると「直った状態」がケースになり、
回帰を検出できない。

## 6. トラブル対応

| 症状 | 確認 | 対応 |
|---|---|---|
| 全呼び出しが失敗する | `claude -p "ping" --output-format json` | Claude Code側の問題。ELFは `chat-fallback` に落ちるので `degraded` で検出できる |
| `QuotaExceeded` が出る | `llmops budget show` | 予算到達。意図的なら `llmops budget set` で引き上げる。意図せずなら原因のtraceを特定する |
| `LLMBudgetExceeded` が出る | `llmops trace show <id>` | 1trace内の呼び出しが上限(既定10回)に到達。無限ループの疑い。**上限を上げる前に原因を見る** |
| `PromptNotPublished` | `llmops prompt show <id>` | 状態が published でない。approve → publish を通す |
| spanが記録されない | `logs/llmops.log` の WARN | Tracerがbest-effortで握り潰している。DBロック・ディスク容量を確認 |
| 応答のcost/tokenがNULL | `spans.raw_response_json` を見る | `claude` CLI の応答スキーマが変わった可能性。`raw` から再集計できる |
| DBが肥大化 | `du -h data/llmops.sqlite3` | `llmops retention apply --dry-run`(Phase 3) |

## 7. やってはいけないこと

| 禁止 | 理由 |
|---|---|
| `allow_unpublished: true` を本番のまま放置 | 評価ゲートが無効になる。開発時のみ |
| `allow_raw_completion: true` を移行後も残す | Registry管理外の呼び出しが恒久化し、Prompt外部化の意味が消える |
| `--force` publish の常用 | 評価ゲートの形骸化。使うたびに監査ログに残ることを意識する |
| `guard.calls_per_trace_limit` を安易に上げる | 上限に当たるのは大抵バグ。上限は症状であって原因ではない |
| Promptの文言改善と構造変更を同時にやる | どちらが原因でスコアが動いたか分からなくなる |
| 評価スイートに production-failure ケースを追加しない | 数ヶ月でスイートが陳腐化し、評価が通るのに本番が壊れる状態になる |
| 既存5システムのコードを移行手順外で触る | 長期テスト中。回帰が最大のリスク |
