# 要件定義書 — Enterprise LLMOps Framework(ELF)

v1.0 / 対象: 既存5システム(PEP・APAP・Harness・DDE・CGMP)の横断運用基盤

---

## 0. 本書の位置付け

`Enterprise_LLMOps_Framework設計書.md`(19章のVendor Agnostic設計)を、**io の実在する5システムに適用可能な実装要件**へ落とし込んだもの。19章の設計書が「あるべき姿」、本書が「この環境で何をどこまで作るか」を定義する。

19章設計書との対応は各要件に `[§n]` で示す。

| # | 課題 | 実コード上の根拠 | 該当アンチパターン |

### 1.3 既に解決済みで**再実装してはならない**もの

ELFの最大のリスクは「6個目の車輪の再発明」である。以下はJVM側に既に存在し、ELFは**契約を合わせるだけ**とする。

| 機能 | 既存実装 | ELFの扱い |
|---|---|---|
| Provider抽象化 / Routing / Fallback / Circuit Breaker | APAP `apap-routing` / `apap-execution` | **委譲**。ELFのGatewayはAPAPと同じ論理モデル名体系を使い、JVM環境ではAPAPへ委譲する |
| Cache / Cost / Quota | APAP `apap-cache` / `apap-cost` | **委譲**(JVM)。Python側は同一契約の最小実装を持つ |
| Prompt資産管理・ライフサイクル | PEP(Draft→Review→Approved→Published→Deprecated→Archived) | **契約準拠**。Python側Registryは同じ状態機械・同じ `id@version` 体系を使う |
| Agent実行 / 承認ゲート / パイプライン状態管理 | Harness `app/harness/pipeline.py` `job_queue.py` `cost_guard.py` | **委譲**。ELFはHarnessにObservability/Registryを注入する側に回る |

## 2. 目的

ELF は **6個目のアプリケーションではなく、既存5システムを横断する Control Plane** である。

1. Prompt・Model・Knowledge・Agent を、システムを跨いだ**単一の資産台帳**で管理する `[§1.3, §14]`
2. Python側3システム(Harness・DDE・CGMP)の LLM 呼び出しを**単一のGateway実装に統合**し、重複実装(C-02)を解消する `[§2, §3]`
3. 全LLM呼び出しの Trace・Token・Cost を**単一のSQLiteに集約**し、横断観測を可能にする `[§9, §13]`
4. Prompt変更に**評価ゲート**を設け、無検証の本番反映を構造的に不可能にする `[§8]`
5. JVM側(PEP・APAP)と Python側の**契約を一致**させ、将来どちらに寄せても資産が失われない状態を作る `[§3, §15]`

## 4. 機能要件

### 4.1 Gateway / Model(Phase 1)`[§3, §12]`

| ID | 要件 | 受入条件 |
|---|---|---|
| FR-010 | 全LLM呼び出しは `llmops.gateway.Gateway` を経由する | DDE/CGMP/Harnessが `subprocess.run(["claude"...])` を直接呼ぶ箇所がgrepで0件 |
| FR-011 | 論理モデル名でモデルを参照する(`chat-standard` 等)。実Providerへの解決はRegistryが行う | アプリコードに `claude` / `anthropic` / 具体モデル名が出現しない |
| FR-012 | Provider Adapterは `claude_cli` / `anthropic_sdk` / `mock` の3種を実装し、SPIで追加可能 | 新Adapter追加がGateway本体の変更なしに可能 |
| FR-013 | 既存 `LLMClient.call_json()` / `call_text()` と**同一シグネチャ**の互換shimを提供する | CGMPの移行差分がimport文の変更のみで済む |
| FR-014 | Provider失敗時に代替論理モデルへFallbackする | `claude_cli` 失敗時に `mock` または別Adapterへ切替わる統合テストが通る |

### 4.2 Prompt(Phase 1)`[§4]`

| ID | 要件 | 受入条件 |
|---|---|---|
| FR-020 | PromptはPythonコードではなく `prompts/**/*.md`(front matter付き)で管理する | `cgmp/llm/prompts.py` の文字列定数が0件になる |
| FR-021 | `prompt_id@version` で参照する。状態は Draft→Review→Approved→Published→Deprecated→Archived(PEP準拠) | Published以外のPromptは本番実行でエラーになる |
| FR-022 | 変数は型付きスキーマで宣言し、レンダリング時に検証する | 未定義変数・型不一致がレンダリング前に検出される |
| FR-023 | レンダリング結果のハッシュ(renderHash)が決定的である(PEP `tests/prompt-regression` と同方式) | 同一入力で同一ハッシュが出る回帰テストが通る |
| FR-024 | Prompt Catalog を CLI で一覧・検索できる | `llmops prompt list --tag cgmp` が動く |

### 4.3 Observability / Cost(Phase 1)`[§9, §13]`

| ID | 要件 | 受入条件 |
|---|---|---|
| FR-030 | 全呼び出しを `traces` / `spans` に記録する(trace_id で親子連結) | 1記事生成が1 trace・N spanとして辿れる |
| FR-031 | `claude -p` 応答の `total_cost_usd` / `usage.input_tokens` / `usage.output_tokens` / `duration_ms` / `session_id` / `num_turns` を全て保存する | 破棄フィールドが0になる |
| FR-032 | 各spanに `prompt_id@version` / `logical_model` / `resolved_provider` / `render_hash` を刻印する | 任意の出力から使用資産を完全逆引きできる |
| FR-033 | 日次/週次のコスト・品質レポートをMarkdownで出力する | `llmops report cost --since 7d` が動く |
| FR-034 | 予算上限(月額)超過時にHard Quotaで呼び出しを拒否する `[§13]` | 上限超過で `QuotaExceeded` が送出され、以後の呼び出しが止まる |

### 4.4 Evaluation(Phase 2)`[§8]`

| ID | 要件 | 受入条件 |
|---|---|---|
| FR-040 | ゴールデンデータセットに対する自動評価を実行できる | `llmops eval run --suite cgmp-outline` が動く |
| FR-041 | 決定的評価(スキーマ準拠・禁止語・長さ)を先に実行し、失敗時はLLM評価に進まない(CGMP絶対ルール6と同方針) | 決定的評価失敗時のLLM呼び出し回数が0 |
| FR-042 | Prompt変更時に回帰テストを実行し、既存ケースのスコア劣化でデプロイをブロックする | 劣化時に `llmops prompt publish` が非ゼロ終了する |
| FR-043 | LLM-as-Judge を使う場合、Judge自身も論理モデル名・Prompt版で管理する | Judge用Promptが `judge/*.md` としてRegistryにある |
| FR-044 | Groundedness評価をCGMPのRAG出力に対して実行できる `[§6]` | context無し断定が検出される |

### 4.5 Governance / Deployment(Phase 3)`[§12, §14]`

| ID | 要件 | 受入条件 |
|---|---|---|
| FR-050 | Prompt/Modelの本番反映はポインタ切替で行い、ロールバックが1コマンドで済む | `llmops prompt rollback <id>` が5分以内に完了 |
| FR-051 | Canary(利用割合指定)で新Prompt版を段階適用できる | 割合設定に従って新旧が振り分けられる |
| FR-052 | 全AI資産に所有者・用途・最終利用日を持たせ、未使用資産を棚卸できる | `llmops catalog stale --days 90` が動く |
| FR-053 | Policy違反(未承認Prompt使用・予算超過・禁止Provider)を監査ログに記録する | `audit_logs` に記録され、CLIで参照できる |

## 5. 非機能要件 `[§16]`

| ID | 要件 | 値 |
|---|---|---|
| NFR-01 | Gateway追加オーバーヘッド | LLM呼び出し1回あたり50ms以内(`claude -p` の起動コストが秒単位のため相対的に無視できる範囲) |
| NFR-02 | Trace捕捉率 | 100%(成否・例外を問わず記録。記録失敗でアプリを止めない) |
| NFR-03 | 可搬性 | ELF単体で動作し、DDE/CGMP/Harnessが未導入でも壊れない |
| NFR-04 | 後方互換 | 既存3システムの移行差分は import 変更 + config 追記のみ |
| NFR-05 | 依存 | 追加の必須依存は Typer / PyYAML / pydantic のみ。RAG/評価用の重い依存は optional extra |
| NFR-06 | 保守性 | 全モジュールが単体でテスト可能。LLM呼び出しは `mock` Adapterで完全に差し替え可能 |
| NFR-07 | 拡張性 | 新Provider追加は `adapters/` にファイル1つ追加で完結(Gateway本体の変更不要) |

## 6. 制約事項

1. **有料サービス使用禁止**(DDE/CGMPの絶対ルール1を継承)。ELF自体が課金を発生させない。既存Harnessが使うAnthropic SDKは「既存の範囲内」として扱い、ELFは呼び出しを**記録・制限**する側に回る
2. **確認質問をしない**(io の標準作業方針)。設計に無い事項は最小実装を選び `NOTES.md` に記録する
3. **既存5システムのDBスキーマを破壊変更しない**。ELFは自分のDB(`data/llmops.sqlite3`)を持ち、既存DBには読み取りでのみ接触する
4. **JVM側(PEP/APAP)のコードを本Phaseでは変更しない**。契約(JSON Schema / 論理モデル名 / Prompt状態機械)を合わせるに留める
5. Python 3.11+(DDE/CGMPが3.11+、Harnessが3.12。下限を3.11に合わせる)

## 7. 対象範囲 / 非対象範囲

### 対象
Python側3システム(Harness・DDE・CGMP)のLLM実行経路の統合、Prompt資産の外部化、横断Observability、評価ゲート、資産台帳。

### 非対象
- PEP/APAPのKotlinコード変更(Phase 4以降の検討事項)
- Kubernetes / マルチリージョン / 高可用構成(19章 §15-16 の該当部分。利用者1名のため)
- Fine-tuning / 学習パイプライン
- RAG本体の再実装(CGMPの `rag/` を正とし、ELFは評価と観測のみ提供)
- Web UI(CLI + Markdownレポートで代替。DDEがREST APIを廃止した判断と同じ)

---

## 8. 利用シナリオ

1. **Prompt改善**: `prompts/cgmp/section.md` を編集 → `llmops eval run --suite cgmp-section` で回帰確認 → 劣化なしなら `llmops prompt publish cgmp.section` → CGMPは次回実行から新版を使う(コード変更・再デプロイ不要)
2. **コスト把握**: 週次で `llmops report cost --since 7d --by system` を実行し、DDE/CGMP/Harnessそれぞれの消費を1枚のMarkdownで確認する
3. **障害調査**: 品質の悪い記事のIDから `llmops trace show <request_id>` で、使用Prompt版・モデル・入出力全文・所要時間を辿る
4. **Provider切替**: `claude -p` が不調な日に `models.yaml` の `chat-standard` の解決先を切り替え、アプリ側は無変更で継続する
